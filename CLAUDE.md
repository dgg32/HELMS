# HELMS — Knowledge Graph Pipeline

> **Before changing or flagging code, read [DESIGN_INVARIANTS.md](DESIGN_INVARIANTS.md).**
> The decisions there are deliberate trade-offs (single-user, per-document edges,
> negative caching, …) — not bugs. See also [AGENTS.md](AGENTS.md) for the
> cross-tool agent entry point.

## Architecture overview

PDF documents → Markdown → triple extraction → review → graph DB.

**Hybrid extraction model:**
- **Batch** (`extract.py`): structured LLM call → bulk entity resolution → `*_raw.json` — fast path, all rel types, all docs
- **Agentic retry** (`agents/extraction_agent.py`): on-demand from HTMX UI Step 2 (🥷🏻 Agent Retry) and the CLI (`--rel-type` flag); one rel_type per trigger; LLM calls tools (gleif_search, umls_search) iteratively with full schema constraints — slow path for tough triples the batch missed. Both paths run `check_triples` (with `harvest_dir`) after the merge so the retried rel_type gets `ai_opinion` and a re-coloring pass.

**Harvest self-improvement loop:**
After each Step 3 write, `agents/harvest.py` rebuilds `<project>/harvest/<rel_type>.jsonl` from all reviewed runs. Positive examples (ADD/OVERRIDE/agent_retry/batch, sorted by priority) and negative examples (REJECT, with original doc + quote) are injected into subsequent extraction runs: positives into the system prompt as few-shot anchors; rejections into every chunk's user message as a per-chunk reminder so the model sees them at highest recency, immediately before the document text.

Used by `extract._verify_grounding`, `extraction_agent.add_triple`, `semantic_check_agent._build_items`, `htmx_app._highlight_evidence`. Replaced the old in-`_verify_grounding` regex `_md_norm`/`_quote_in_doc` pair |
| `convert_pdf.py` | PDF → Markdown (pymupdf4llm or llamaparse) |
| `apply_graph.py` | Reads `*_raw.json` + review events → writes to graph DB; **edge identity**: stamps `rel_props["triple_id"] = triple["_id"]` before `create_edge()` so edges are addressable by stable identity, not node pair; **stale-edge deletion**: excluded (color-filtered) + rejected triples each get `delete_edge(..., source_doc=doc_name, triple_id=_t["_id"])` before the write loop — the `triple_id` match removes the prior edge even if a review entity-correction changed its endpoints (the old node-pair-diffing hack is now subsumed by this + `create_edge`'s identity delete); **`mkdir` dry-run guard**: `Path(args.db).parent.mkdir(...)` only called when `not args.dry_run` — dry-run never touches the filesystem |

## Key conventions

**Resolver pattern** — adding a new external data source:
1. Create `agents/xyz_resolver.py`, subclass `NodeResolver`, set `source = "xyz"`, implement `resolve_batch()` and `build_props()`
2. Append instance to `_RESOLVERS` in `agents/node_agent.py`
3. No changes to `extract.py` or other shared code

**Schema properties** — node properties carry `source=`: `"umls"`, `"gleif"`, or `"llm"`.
`NodeResolver.handles(node_def)` matches on this field.

**Run folder layout** — each run lives in `<project>/runs/<timestamp>/`:
- `*_raw.json` — immutable extraction output
- `*_review.json` — mutable event log (REJECT/OVERRIDE/ADD)
- `*_kg.db` — LadybugDB graph
- `run_config.json` — run metadata + extraction stats
- `_node_agent_errors.jsonl` — entities that failed resolution

**Review layer** — `_raw.json` is never modified. Human edits write events to `_review.json`.
`review_layer.materialize(raw, events)` produces the working triple list.

**MCP pipeline stdout** — redirected to `pipeline.log`; prevents JSON-RPC channel corruption.

**LadybugDB read** — `_execute` reopens DB+connection per query when `read_only=True` to see latest checkpoint after writes.

**Async LLM client isolation** — `extract.py` uses `threading.local()` for the async client. Each thread (web UI runner, MCP ingest thread) gets its own `AsyncAzureOpenAI` instance. Never share an async client across `asyncio.run()` calls on different threads.

**Agentic extraction output** — `ExtractionAgent.save_review()` writes `*_raw.json` (same name/format as batch `extract.py`). The HTMX review UI globs only `*_raw.json`; writing `*_review.json` would make the run invisible to the UI.

**`mcp_server.py` write-guard** — write-verb check runs on a copy of the query with all string literals removed (`_STRING_LITERAL_RE.sub`). Do not add logic that reads from the original query string — that's the bypass vector the strip is defending against.

**`_AppState` singleton** — `htmx_app/main.py` holds one in-memory `_AppState` instance. Single-user design; no multi-tenancy. Persists `project_folder`, `run_id`, `filter_level`, `converter`, `backend`, `llm_model` to `htmx_app/.helms_state.json` on every change via `_state.save()`. All route handlers read/write from this singleton.

**Per-triple color override** — clicking the color dot in `tripleCard` calls `cycleColor()` (green→yellow→red→green), updates `data-triple-color` on the DOM element, marks dirty. On save, `triple_color` included in OVERRIDE event. `review_layer.materialize()` applies it so the color survives save and the write filter respects it. Use to promote a correct red triple to green before Step 3 (`moderate` filter drops red by default).

**Editable supporting quote (review UI)** — the quote in `tripleCard` is an editable `<textarea>` (`x-model="quote"`, `@input="markDirty()"`), synced to `data-triple-quote` in `_syncAttrs` and collected by `window._helmsTriples()` as `supporting_quote`. On `/review/save`, an edited quote (only when it differs from the raw original) is **re-anchored against the source `.md`** via `extract._build_evidence([quote], doc_text)` (deterministic `grounding.locate`): stored as `evidence` (source of truth) + derived `supporting_quote` ONLY if a span locates verbatim; otherwise the original is kept and the triple's `_id` is returned in `quote_warnings` (the client toasts a warning). This preserves the "every stored quote is provably in the document" invariant — a free-typed quote that is not in the source is never persisted. The `.md` path is `raw_path.name.removesuffix("_raw.json") + ".md"` (same derivation as `/review/evidence`). Regression: `tests/test_schema.py::TestReviewQuoteOverride`. NOTE: the Add-Triple form still has no quote field — added triples carry no `supporting_quote`; editing is for existing triples only.

**Agent retry cross-component state** — `step2()` and `triplesList()` / `tripleCard()` are nested Alpine components; `triplesList` cannot read `step2` state directly. Shared state lives in `Alpine.store('helms', { agentRunning: false, dirty: false })`, initialized on `alpine:init` before any component. `step2.startAgentRetry()` sets `agentRunning` true; `_onAgentRetryDone()` and `_connectAgentSSE` onerror set it false. `tripleCard.markDirty()`, `triplesList.addTriple()`, and `triplesList.removeAdded()` set `dirty` true directly on the store — document event `helms-mark-dirty` is unreliable for nested components. Agent Retry buttons in `triples_list.html` read `$store.helms.agentRunning` for disabled/opacity. The `⚠ Unsaved changes` badge reads `dirty || $store.helms.dirty`.

**HTMX UI event bus** — Alpine components communicate via `document.dispatchEvent(new CustomEvent(...))`. Key events:
- `helms-run-selected` — fired after run dropdown changes; all steps clear stale data and reload
- `helms-project-changed` — fired (via `HX-Trigger` header) after project select; steps refresh
- `helms:step-done` — `{ step, ok }` — fired by each step's `onDone()`; cross-step coordination
- `helms:step-started` — `{ step, token }` — fired when a step starts from another entry point
- `helms:file-select` — `{ rawPath, revPath }` — fired by step2_files dropdown to load triples
- `helms:triple-state-change` — `{ wasRejected, nowRejected, color }` — updates `triplesList` counters
- `helms:agent-retry-rel` — `{ relType }` — fired by Agent Retry button; `step2.startAgentRetry()` listens and triggers the agentic SSE run

**`window._helmsTriples` / `window._helmsAddedTriples`** — set by `triples_list.html` after HTMX swap. Read by `step2._flushReview()` to collect current triple state from DOM `data-triple-*` attributes. Not available before a review file is loaded.

**SSE keepalive** — `/stream/{token}` yields `: keepalive\n\n` comment when queue is empty (every 0.5 s). This prevents proxy/browser connection timeout. The `done` SSE event closes the stream; `es.onerror` with `readyState === CLOSED` handles abnormal closure.

**Schema editor soft-fields-only** — `/schema/save` merges only: node `description`, `sem_group`, `umls_vocabs`, `semantic_types`; rel `from_hint`, `to_hint`, `extract_prompt`, `examples`, and LLM prop `hint`. All other YAML keys (node property list, `rel_type`, `from_node`, `to_node`, `from_field`, `to_field`) are left untouched. Schema is validated via `_SchemaDef.model_validate()` before write.

**Quality + unresolved endpoints** — `GET /review/quality` returns green/yellow/red/rejected/added/active counts per `*_raw.json` file; consumed by step2's quality panel. Uses `_rl.materialize(raw_data, events)` for color counts so OVERRIDE color changes are reflected immediately after save. `GET /review/unresolved` reads `_node_agent_errors.jsonl` from current run folder; returns first 50 entries + total count; consumed by step2's unresolved UMLS panel.

**Stale-edge deletion** — `apply_graph.py` computes an `_excluded_triples` list (color-filtered + rejected triples) before the write loop. For each excluded triple it calls `backend.delete_edge(..., source_doc=doc_name, triple_id=_t["_id"])`. `source_doc` scopes the delete to the re-run document (other documents' edges survive); `triple_id` makes the match endpoint-independent, so an edge whose entity was corrected in review is removed under its OLD identity too. This prevents stale/orphaned edges after a reject or entity-correction re-run.

**Edge identity = `triple_id`, not node pair** — `apply_graph.py` stamps `rel_props["triple_id"] = triple["_id"]` (the immutable raw hash) onto every edge. `create_edge` and `delete_edge` prefer an endpoint-independent `{triple_id, source_doc}` match (falling back to node-pair + `source_doc` for legacy edges without `triple_id`). This is the structural fix for orphaned edges: when a reviewer OVERRIDEs a wrongly-resolved entity (changing the from/to PK), the corrected triple keeps the same `_id`, so the re-run deletes the old-identity edge instead of leaving it behind. NOT node-pair dedup — `source_doc` still scopes every delete (invariant #2). Existing DBs must be rebuilt to gain the `triple_id` column.

**LiteLLM provider routing** — `llm_client.get_provider()` returns `azure` (default when `LLM_ENDPOINT` set + `LLM_PROVIDER` unset), `openai`, `openai_compatible`, `anthropic`, `ollama`, or `gemini`. `openai_compatible` is for OpenAI-shaped gateways (OpenCode Go, OpenRouter, vLLM): `_get_litellm_model` keeps the `openai/` prefix and `_litellm_kwargs` adds `api_base = LLM_ENDPOINT.rstrip("/")` so LiteLLM POSTs to `{base}/chat/completions`; it is a DISTINCT provider from `openai` on purpose, so a stray global azure `LLM_ENDPOINT` can never reroute a plain-`openai` call (regression-guarded by `tests/test_schema.py::TestOpenAICompatibleProvider`). Caveat: these gateways must honour native `response_format` JSON-schema structured output or extraction fails validation. **All providers route through `_acreate_litellm`** — no separate Azure/OpenAI SDK path. `litellm.acompletion` + `response_format=response_model` + Pydantic `model_validate_json()` used universally. `_ensure_litellm_env()` clears all known provider keys before setting the current one — prevents key leakage when switching providers at runtime. `litellm.suppress_debug_info = True` set in every file that imports litellm to suppress "Provider List" terminal noise.

**Independent grader model (`SEMANTIC_CHECK_MODEL`)** — the semantic-check LLM pass can run on a different model AND provider than extraction, so no model grades its own output. `semantic_check_agent._call_llm_batch` reads `SEMANTIC_CHECK_MODEL` and resolves the grader's model + creds via **`llm_client.model_call_params(name)`**, passing the returned `(full_model, call_kwargs)` as EXPLICIT kwargs to `litellm.completion` — it does NOT mutate `os.environ`. **This non-mutation is a hard requirement, not a style choice:** the semantic check runs in `await asyncio.to_thread(check_triples, …)` ([extract.py](extract.py) ~line 1131) CONCURRENTLY with other documents' extraction, which reads the same global env; the earlier env-swapping approach (`use_model_env`) raced and sent the extraction model id to the grader's provider (symptom: `AzureException NotFoundError - deployment does not exist` on a MiMo-extraction run with a gpt-5.5 Azure grader). `model_call_params`: empty/None ⇒ current env; a name in `.env.yaml` `models:` ⇒ that entry's full provider/model/key/base computed into a LOCAL dict (model-identifying `_MODEL_ENV_KEYS` taken ONLY from the entry, no stale-endpoint leak); a bare name not in config ⇒ current provider/creds, model id swapped. The env-reading helpers (`get_provider`/`_get_litellm_model`/`_litellm_kwargs`/`_base_url`/`_deployment`) take an optional `env` mapping (default `os.environ`) so params can be built from the local dict. `use_model_env` (the env-mutating context manager) is RETAINED for single-threaded/sequential callers only and is documented NOT thread-safe — never use it on the concurrent grader path. Extraction (`acreate_structured_output`) is untouched. Regression: `tests/test_schema.py::TestModelCallParams` (incl. the non-mutation guarantee) + `TestUseModelEnv::test_call_llm_batch_routes_via_kwargs_without_env_mutation`.

**triple_color on graph edges** — `apply_graph.py` writes `triple_color` from each triple into the edge's `rel_props` before `create_edge()`. `ladybug_backend.setup()` auto-injects `triple_color STRING` (and `triple_id STRING`) into every rel table DDL. `query_graph.py` returns `r.triple_color` in every edge query. To style edges in NVL: `WHERE r.triple_color = 'red'`. Existing DBs without the columns must be deleted and rebuilt.

**Shared `acreate_structured_output`** — async LLM retry loop lives in `llm_client.py`. Signature: `acreate_structured_output(text_input, system_prompt, response_model, model, max_completion_tokens, timeout, retries, base_delay, log_prefix)`. No `get_client` param — all providers go through LiteLLM internally. Add a `log_prefix` to distinguish callers in logs. Never duplicate this loop in other modules.

**Semantic type mismatch** — `_deterministic_flags` in `semantic_check_agent.py` checks actual vs expected UMLS semantic types whenever `schema_nodes` has `semantic_types` defined, regardless of filter level. `_build_items` injects `{from,to}_expected_semantic_types` and `{from,to}_actual_semantic_types` so the LLM batch sees the mismatch. A mismatched type sets `constraint_violated=true` and colors the triple red. Do NOT re-gate this check on `filter_level == "strict"`.

**Harvest rejection enforcement in semantic check** — `check_triples` accepts `harvest_dir: Path | None`. When provided, it scans all `*.jsonl` files in that directory for entries with `source="rejected"` and builds a `rejected_logical` set of `(rel_type, from_display, to_display)` tuples. After the LLM and structural checks run, any triple whose logical key matches is forced red (`triple_color="red"`, `constraint_violated=True`) and gets `"[Previously rejected by human reviewer]"` appended to `ai_opinion`. This check runs unconditionally after the LLM verdict — it overrides even a green LLM result. Human can still cycle the color dot to green in the UI if the current document provides stronger evidence (doc-specific semantics preserved). Three callers pass `harvest_dir`: `extract.py` (post-batch), `htmx_app/main.py` `_run_agent_semantic_check` (HTMX agent retry), and `agents/extraction_agent.py` `_cli_semantic_check` (CLI agent retry).

**`get_backend` setup param** — `get_backend(name, db_path, nodes, rels, read_only=False, setup=True)`. Pass `setup=False` when the backend must not run DDL (e.g. `mcp_server.py` opens Ladybug read-only; `CREATE TABLE IF NOT EXISTS` would fail). Always pass `setup=True` (default) for write paths.

**GLEIF entity disambiguation** — `gleif_resolver.py` uses a three-stage pipeline: (1) gather candidates via `gleif_get_candidates` (exact+names+fuzzy+WHO OWNS parents); (2) for short all-caps abbreviations (≤6 chars) with no strong direct candidate, expand to a full legal name and merge those candidates — source order `ctx.abbr_map` (doc-defined, no LLM) → `_ABBREV_TABLE` (static, no LLM) → `_expand_abbreviation()` (LLM fallback); (3) pick the winner with `domain_hint` — if LLM returns index=0, the `retry_search_term` carries the LLM's suggested full name; code retries `gleif_get_candidates` with that term and re-picks. `domain_hint` and `abbr_map` ride in a `ResolveContext` from `meta.yaml` `instructions` + `extract._extract_abbreviations` threaded through `extract.py` → `resolve_all_nodes` → `resolve_batch`. Do NOT skip the retry step — it's the only way "Murata" resolves to "Murata Manufacturing Co., Ltd." when no candidates match "Murata" verbatim.

**Quote re-anchoring (`grounding.py`)** — `grounding.py` (project root) is the single token-based quote locator shared by all paths. `extract._verify_grounding` and `extraction_agent.add_triple` both call `grounding.reanchor(quote, doc_text)`: a located quote is OVERWRITTEN with the verbatim `doc_text[start:end]`, so the stored quote is guaranteed-in-document and downstream (triple build, semantic check, harvest, display) never sees LLM quote drift. The per-edge quotes are then turned into `evidence: [{start,end,text}]` by `extract._build_evidence` (offsets re-located deterministically, the LLM is never asked for positions); **`supporting_quote` is DERIVED from `evidence`** (`/`-joined `text`), so `evidence` is the grounding source of truth and `supporting_quote` is a display/graph projection. Unlocatable quotes warn (moderate) / drop (strict). `_verify_grounding` runs on `all_items` BEFORE triple building, so the re-anchored quote flows into the triple's `supporting_quote` and then into `check_triples`. The matcher tolerates markdown, curly/ASCII quote swaps, blanked `([[N]] url)` citations + HTML tags, bullet/trademark glyphs, and `...` elisions; the span covers matched word cores (edge markup + sentence period excluded). **Multi-segment rescue**: when the whole quote does not locate, `_verify_grounding` splits it on `_QUOTE_SEGMENT_SPLIT` (` / `, ` * `, ` - `, ` • ` — the separators the LLM uses to stitch non-adjacent fragments, e.g. a list intro paired with one bullet item), re-anchors each segment, and stores the ` / `-joined verbatim segments only if EVERY segment locates (partial → warn/drop). A grounding warn is informational only — it does NOT recolor or empty the triple; the original LLM quote is kept and the semantic check colors it normally. Known residual misses (left to warn, not bugs): italic-underscore-split hyphen compounds (`difficile-associated` vs `_C. difficile_ -associated` = 1 token vs 2) and long comma-lists under italic headers. Do NOT reintroduce a regex `_md_norm`/`_quote_in_doc` pair — that was the brittle approach this replaced.

**Color authority is the semantic-check agent ONLY** — extraction does NOT color triples. Both the batch path (`extract.py` edge build) and the agentic path (`extraction_agent.add_triple`) stopped calling `_classify_entity`; `_COLOR_RESOLUTION_RANK` was deleted. `semantic_check_agent.check_triples` is the single place `from_color`/`to_color`/`triple_color` are set, and it always runs before the color filter (batch) or writes colors back to `*_raw.json` (agentic, via `_run_agent_semantic_check`/`_cli_semantic_check`). `_classify_entity` is retained only for tests. Degradation: if the semantic check is skipped (e.g. no LLM creds), triples are uncolored and default to green at every `.get("triple_color","green")` read. Do NOT re-add coloring to extraction.

**Evidence spans (`evidence`) are the grounding source of truth** — each triple carries `evidence: [{start, end, text}]`, built by `extract._build_evidence` (batch) / `extraction_agent.save_review` (agentic). Offsets come from `grounding.locate` at extraction time — the LLM is NEVER asked for char positions. `supporting_quote` is a DERIVED projection (`/`-joined `text`) kept for display, the graph edge, and harvest back-compat. `semantic_check_agent._build_items` consumes `evidence` directly (`quote_verbatim` true only when EVERY span located; `quote_context` sliced straight from offsets, no re-locate), with a legacy fallback that splits `supporting_quote` on `" / "` for runs predating the field. `evidence` lives only in `*_raw.json` — it is NOT written to the graph (offsets have no KG query value); `apply_graph` writes only `supporting_quote` + `triple_color` onto the edge, identically for LadybugDB and Neo4j. Three concerns are now separated: provenance (`evidence` spans), presence (deterministic offsets), color/relation (semantic check).

**Batched resolver picks** — both `gleif_resolver.py` and `umls_resolver.py` `resolve_batch` run two phases: Phase A (per-entity, concurrent) does cache check (L1/L2) + candidate gather (`_gather_candidates`, threaded HTTP) + no-LLM `_prefilter` (single-candidate / exact-name shortcuts); Phase B sends only the *ambiguous remainder* to `_batch_llm_pick` in one structured `_BatchPickResult` call per ≤12 entries (GLEIF adds a single follow-up batch for index=0 `retry_search_term`s). This replaces one-LLM-call-per-entity (concurrency hid latency but not cost/tokens); ~32 entities → ~3–4 pick calls. Cache writes happen in both phases via `_cache_store`. Per-entity `_resolve_one`/`_do_resolve_one` are RETAINED (they call `_gather_candidates`/`_prefilter` + a single `_llm_pick_best`) for the single-entity path and the cache tests in `tests/test_schema.py` — do not delete them.

**`_node_allowed_props` filtering** — `ladybug_backend.setup()` builds `_node_allowed_props[label]` from schema-declared columns + system columns (`run`). `upsert_node()` filters `props` dict through this set. Without this, any extra props a resolver returns (GLEIF returns `status`, `jurisdiction`, `registration_status` not always in schema.yaml) would cause a LadybugDB "column not found" error. If you add a resolver that returns extra fields, either add those fields to schema.yaml or they will be silently dropped — check `_node_allowed_props` to confirm.

**LadybugDB close and read-only** — Always call `backend.close()` after a write session. `LadybugBackend.close()` deletes `self._conn` and `self._db`, releasing LadybugDB's internal background subprocess and file lock. A no-op close (the base class default) leaves the lock held, causing the next Step 3 to hang. For read-only access (graph summary, MCP server), use `get_backend(..., read_only=True, setup=False)` — `setup=False` skips DDL that would fail in read-only mode; `read_only=True` reopens DB+connection per query to see the latest checkpoint.

**Harvest self-improvement** — `harvest_project()` always rebuilds the store from scratch (never patches in-place) so REJECT events are honoured immediately. Priority tiers: add=1 (human-written) → override=2 (human-corrected) → agent_retry=3 → batch=4. `load_examples()` diversifies positives by `to_display` (avoids same target entity repeated). Rejected triples are stored as negative examples with `source: "rejected"` — do NOT manually edit the JSONL files; edits are overwritten on the next rebuild. Rejections are doc-specific: the prompt tells the LLM it may re-extract a rejected triple if the current document provides clearly stronger evidence. Rejection reminders are injected into every chunk's user message (not just the system prompt) so they appear at highest recency immediately before the document text. Cache invalidation: the chunk cache key now includes `_harvest_signature(harvest_dir)` (a content hash of `harvest/*.jsonl`), so adding a rejection or example invalidates affected cached chunks automatically — `--force` is no longer required after rejecting a triple. **Positive few-shot examples are labeled as STYLE PATTERNS, not an exhaustive whitelist** (`format_examples_block` header explicitly tells the model to extract EVERY matching pair, including ones absent from the examples) to avoid the recall collapse where a small model parrots the examples and skips the long tail.

**Selective failed-chunk retry** — `process_document` extracts each chunk via the `_run_chunk(i)` closure (cache check + LLM call). The first pass records 1-based indices of chunks whose LLM call raised into `_failed_chunks`; then up to `chunk_retries` (CLI `--chunk-retries`, default 1) follow-up passes re-run ONLY those indices. Cache hits and already-successful chunks are never touched, so retries cost no extra LLM calls. `asyncio.TimeoutError` is re-raised (not retried here) so the doc-level retry loop in `main()._process` (`--retries`) handles it. Results are accumulated from `results_by_idx` in index order after all passes complete. `pipeline_ns.build_extract_ns()` does NOT set `chunk_retries`; `main()` reads it via `getattr(args, "chunk_retries", 1)`, so the UIs get the default 1 automatically.

**Pre-flight estimate** — `_preflight_estimate()` runs unconditionally at the top of `extract.main()` (so the web UI and CLI all print it to the log) before any LLM call. It mirrors the skip logic (`*_raw.json` exists ⇒ skipped), runs the real `_semantic_chunk_text` chunker for an accurate chunk count, estimates input tokens at ~4 chars/token plus a per-chunk static-prompt overhead, and prices input via `litellm.cost_per_token(model=_get_litellm_model(), …)` (best-effort; wrapped in try/except — cost line is skipped if the model isn't in litellm's table). `--estimate-only` (read via `getattr(args, "estimate_only", False)`) prints the estimate and returns `[]` before extracting.

**Lookup cache maintenance + TTL** — `lookup_cache.py` is the L2 store; eviction/TTL exist because a wrong resolution would otherwise persist forever. `python -m lookup_cache stats|evict <substring> [--service X]|clear [--service X] [--yes]`. `LOOKUP_CACHE_TTL_DAYS` (default `30` days; `0` disables, restoring never-expire behavior) is read at module import — must be a real shell env var set BEFORE launch, not a `.env` entry (import precedes dotenv load). Two L-level caveats: (1) the L1 in-process dicts in `lookups.py` have no TTL/eviction hook; (2) a CLI `evict` deletes from L2 SQLite only, so a long-running HTMX server keeps serving an already-L1-cached value until restarted. If you add an L1 flush hook, wire it into `lookups.py` (`_gleif_cache`, `_umls_cache`, `_gleif_candidates_cache`, `_umls_pick_cache`, `_gleif_pick_cache`).

**Hybrid deterministic + LLM grounding (maximize the rule-checkable slice)** — the semantic check is split on a simple principle: anything provable by a rule must be a rule, not an LLM judgment, because rules are consistent run-to-run and LLM judgments are not (measured: gpt-5.5 flipped the same present entity red↔yellow/green across two identical runs). Concretely: `EntityPresenceValidator` proves an entity is named in its own quote (`grounding.locate` against the resolved name, the raw extracted term gated by resolver source, and any resolver-supplied `synonyms`) and pins it green via a `from_color_anchor`/`to_color_anchor` on `Verdict` — the INVERSE of `color_floor` (floor raises toward red, anchor raises an entity toward green), entity axis only, never touching `constraint_violated`. `RelationSupportHintValidator` precomputes advisory facts (`relation_endpoints_colocated`, `possible_negation_in_quote`) so the LLM spends its budget on the genuinely hard part — relation support and direction — instead of re-deriving bookkeeping it can't do reliably. When adding a new check, ask "can this be a rule?" first; only fall back to an LLM judgment for what truly requires language understanding (paraphrase, support, direction). A/B on gpt-5.5 validated the anchor: 0 false-reds / 0 cross-run variance vs the no-anchor baseline's 1 false-red + 1/77 unstable. See [DESIGN_INVARIANTS.md](DESIGN_INVARIANTS.md) #3 for the full writeup.
